\section{State and named invariants}

The provider and harness are opaque names. A report is a curated progress
snapshot, not a hook history. Pending cleanup is orthogonal to process lifecycle:
a failed cleanup is durable and retried even when the lifecycle is terminal.

\begin{zed}
  [WORKER, REPORT, RESULT] \\
  Phase ::= starting | ready | exited | stopped \\
  Event ::= sessionStart | update | stopHook | sessionEndHook
\end{zed}

\begin{schema}{Workers}
  phase : WORKER \pfun Phase \\
  report : WORKER \pfun REPORT \\
  readySeen, pending : \power WORKER
\where
  \dom phase = \dom report \\
  readySeen \subseteq \dom phase \\
  pending \subseteq \dom phase \\
  \forall w : \dom phase @ phase~w = ready \implies w \in readySeen
\end{schema}

Named invariants checked by implementation tests are:
\textbf{durable intent} (launch follows record persistence),
\textbf{ready continuity} (a live ready worker never regresses),
\textbf{report freshness} (a delivered report replaces the previous snapshot),
\textbf{terminal stability} (repeated stop does not change a terminal phase),
\textbf{retryable cleanup} (terminal does not imply cleanup succeeded), and
\textbf{unknown identity refusal} (controls require an existing worker).
Unavailability is not evidence of death. Every omitted state component is framed
explicitly below. Explicit stop attempts provider termination, then checkpoints
the terminal phase with pending cleanup before scheduling harness cleanup.
If the daemon stops before cleanup runs, the durable pending marker lets
recovery retry it rather than leaving the trust entry behind.
Hook delivery receipts follow the curated report checkpoint; receipt is never
issued for an uncommitted readiness transition.

\begin{schema}{InitWorkers}
  Workers
\where
  phase = \emptyset \\
  report = \emptyset \\
  readySeen = \emptyset \\
  pending = \emptyset
\end{schema}

\begin{schema}{StartWorker}
  \Delta Workers \\
  worker? : WORKER \\
  initial? : REPORT
\where
  worker? \notin \dom phase \\
  phase' = phase \cup \{worker? \mapsto starting\} \\
  report' = report \cup \{worker? \mapsto initial?\} \\
  readySeen' = readySeen \\
  pending' = pending
\end{schema}

\begin{schema}{ObserveLiveReport}
  \Delta Workers \\
  worker? : WORKER \\
  fresh? : REPORT \\
  event? : Event \\
  next? : Phase
\where
  worker? \in \dom phase \\
  phase~worker? \in \{starting, ready\} \\
  next? \in \{starting, ready\} \\
  (phase~worker? = ready \lor event? = sessionStart) \implies next? = ready \\
  (phase~worker? = starting \land event? \neq sessionStart) \implies next? = starting \\
  phase' = phase \oplus \{worker? \mapsto next?\} \\
  report' = report \oplus \{worker? \mapsto fresh?\} \\
  next? = ready \implies readySeen' = readySeen \cup \{worker?\} \\
  next? = starting \implies readySeen' = readySeen \\
  pending' = pending
\end{schema}

The ready value of next? requires either a previous ready phase or an observed
SessionStart. Missing hook-store state and provider unavailability are no-ops;
neither supplies a fresh report nor a new liveness fact.

\begin{axdef}
  mergeTerminal : REPORT \cross Event \cross \nat \cross REPORT \fun REPORT \\
  result : REPORT \fun RESULT \\
  resultSequence : RESULT \fun \nat
\where
  \forall saved, delivered : REPORT; seq : \nat @
    result~(mergeTerminal(saved, sessionEndHook, seq, delivered)) = result~saved \\
  \forall saved, delivered : REPORT; seq : \nat |
    seq < resultSequence~(result~saved) @
    result~(mergeTerminal(saved, stopHook, seq, delivered)) = result~saved
\end{axdef}

\begin{schema}{ObserveExitedReport}
  \Delta Workers \\
  worker? : WORKER \\
  event? : Event \\
  sequence? : \nat \\
  delivered? : REPORT
\where
  worker? \in \dom phase \\
  phase~worker? = exited \\
  event? \in \{stopHook, sessionEndHook\} \\
  report' = report \oplus
    \{worker? \mapsto mergeTerminal(report~worker?, event?, sequence?, delivered?)\} \\
  phase' = phase \\
  readySeen' = readySeen \\
  pending' = pending
\end{schema}

The exited phase includes an exit confirmed and checkpointed by listing.
Only a registered worker's
Stop or SessionEnd from its worktree can take this transition. The merge
starts from the saved projection and respects its hook sequence ordering;
SessionEnd does not erase a saved result. The merged report also becomes
visible in shared hook context under ordinary retention.

\begin{schema}{ObserveMissingOrUnavailable}
  \Xi Workers \\
  worker? : WORKER
\where
  worker? \in \dom phase
\end{schema}

\begin{schema}{TerminateWorker}
  \Delta Workers \\
  worker? : WORKER \\
  terminal? : Phase
\where
  worker? \in \dom phase \\
  phase~worker? \in \{starting, ready\} \\
  terminal? \in \{exited, stopped\} \\
  phase' = phase \oplus \{worker? \mapsto terminal?\} \\
  report' = report \\
  readySeen' = readySeen \\
  pending' = pending \cup \{worker?\}
\end{schema}

Confirmed provider death selects exited; explicit stop and successful launch
rollback select stopped. If rollback cannot confirm termination, starting is
retained with a durable launch error and explicit stop can retry termination.
After the termination checkpoint, \textit{RetryCleanup} records the outcome.
Cleanup success removes the pending marker. On failure it remains, and an error
may be attached to the opaque report without changing process phase. The model
does not distinguish an exited pane from its remaining tmux session. Explicit
stop can still remove that session once without changing the exited phase.

\where

  next? \in \{starting, stopped\} \\

  report' = report \oplus \{worker? \mapsto failure?\} \\
  readySeen' = readySeen \\
  pending' = pending \cup \{worker?\}
\end{schema}

\begin{schema}{RetryCleanup}
  \Delta Workers \\
  worker? : WORKER \\
  remaining? : \power WORKER \\
  result? : REPORT
\where
  worker? \in pending \\
  remaining? \subseteq \{worker?\} \\
  pending' = (pending \setminus \{worker?\}) \cup remaining? \\
  report' = report \oplus \{worker? \mapsto result?\} \\
  phase' = phase \\
  readySeen' = readySeen
\end{schema}

\begin{schema}{RepeatTerminalStop}
  \Xi Workers \\
  worker? : WORKER
\where
  worker? \in \dom phase \\
  phase~worker? \in \{exited, stopped\} \\
  worker? \notin pending
\end{schema}

\section{Steering state and invariants}

Steering observes input or a pending dialog's next hook, not turn completion.
For dialogs, receiptText records the delivered words, not a fabricated prompt
event or evidence of approval. Time is monotonic milliseconds;
the pre-delivery budget is 10,000 ms across both lock waits, not a fresh budget
per lock. Delivery is the atomic admission of provider input under the actor
lock, after its final deadline and readiness checks. Provider I/O and paste
settling are abstracted by this admission; this model does not bound arbitrary
backend execution time. Receipt polling has a separate 10,000 ms budget.

\begin{zed}
  [STEER, WORDS, DIRECTORY] \\
  SteerPhase ::= queued | locked | sent | acknowledged | unheard | refused
\end{zed}

\begin{schema}{Steering}
  now : \nat \\
  steerPhase : STEER \pfun SteerPhase \\
  target : STEER \pfun WORKER \\
  words : STEER \pfun WORDS \\
  deadline : STEER \pfun \nat \\
  inFlight : WORKER \pinj STEER \\
  baseline, sentAt, receiptDeadline : STEER \pfun \nat \\
  admittedPhase : STEER \pfun Phase \\
  receiptSeq : STEER \pfun \nat \\
  receiptText : STEER \pfun WORDS \\
  accepted, endedByReceipt : \power STEER
\where
  \dom steerPhase = \dom target \\
  \dom target = \dom words \\
  \dom words = \dom deadline \\
  \ran inFlight = \{ r : \dom steerPhase | steerPhase~r \in \{locked, sent\} \} \\
  \forall w : \dom inFlight @ target~(inFlight~w) = w \\
  \dom baseline = \{ r : \dom steerPhase | steerPhase~r \in \{sent, acknowledged, unheard\} \} \\
  \dom sentAt = \dom baseline \\
  \dom receiptDeadline = \dom baseline \\
  \dom admittedPhase = \dom baseline \\
  \forall r : \dom baseline @ admittedPhase~r = ready \land sentAt~r < deadline~r \\
  accepted = \{ r : \dom steerPhase | steerPhase~r = acknowledged \} \\
  \dom receiptSeq = accepted \\
  \dom receiptText = accepted \\
  \forall r : accepted @ receiptSeq~r > baseline~r \land receiptText~r = words~r \\
  endedByReceipt = \emptyset
\end{schema}

Named properties: \textbf{only ready workers steered} is the admitted-phase
invariant and the current-phase precondition of Steer. \textbf{At most one
steer in flight per worker} follows from the partial injection inFlight;
queued requests do not own it. \textbf{Receipt freshness and exact text}
require a sequence strictly above the captured baseline and the original
words. \textbf{No delivery after deadline} is sentAt less than deadline.
\textbf{Heard never implies turn ended}: endedByReceipt is a proof-only set of
turn-end claims justified by receipts, invariantly empty, not an idle-state
tracker. Steering operations preserve Workers; neither Escape nor receipt
requires or fabricates a Stop event. A worker may be stopped independently
while awaiting its receipt; admittedPhase records readiness at delivery, not
a promise that lifecycle remains ready afterward.

\begin{schema}{InitSteering}
  Steering
\where
  now = 0 \\
  steerPhase = \emptyset \\
  target = \emptyset \\
  words = \emptyset \\
  deadline = \emptyset \\
  inFlight = \emptyset \\
  baseline = \emptyset \\
  sentAt = \emptyset \\
  receiptDeadline = \emptyset \\
  admittedPhase = \emptyset \\
  receiptSeq = \emptyset \\
  receiptText = \emptyset \\
  accepted = \emptyset \\
  endedByReceipt = \emptyset
\end{schema}

\section{Steering transitions}

QueueSteer accepts an RPC identity and starts its single pre-delivery clock.
WORDS denotes admissible literal input under the harness receipt limit.
Invalid input is refused before provider delivery. AcquireSteering models
only the per-worker lock; waiting for the actor cannot renew deadline.

\begin{schema}{QueueSteer}
  \Delta Steering \\
  \Xi Workers \\
  request? : STEER \\
  worker? : WORKER \\
  words? : WORDS
\where
  request? \notin \dom steerPhase \\
  steerPhase' = steerPhase \cup \{request? \mapsto queued\} \\
  target' = target \cup \{request? \mapsto worker?\} \\
  words' = words \cup \{request? \mapsto words?\} \\
  deadline' = deadline \cup \{request? \mapsto now + 10000\} \\
  (now', inFlight', baseline', sentAt', receiptDeadline') =
    (now, inFlight, baseline, sentAt, receiptDeadline) \\
  (admittedPhase', receiptSeq', receiptText', accepted', endedByReceipt') =
    (admittedPhase, receiptSeq, receiptText, accepted, endedByReceipt)
\end{schema}

\begin{schema}{AcquireSteering}
  \Delta Steering \\
  \Xi Workers \\
  request? : STEER
\where
  request? \in \dom steerPhase \\
  steerPhase~request? = queued \\
  target~request? \notin \dom inFlight \\
  now < deadline~request? \\
  inFlight' = inFlight \cup \{target~request? \mapsto request?\} \\
  steerPhase' = steerPhase \oplus \{request? \mapsto locked\} \\
  (now', target', words', deadline', baseline', sentAt') =
    (now, target, words, deadline, baseline, sentAt) \\
  (receiptDeadline', admittedPhase', receiptSeq', receiptText', accepted', endedByReceipt') =
    (receiptDeadline, admittedPhase, receiptSeq, receiptText, accepted, endedByReceipt)
\end{schema}

\begin{schema}{Steer}
  \Delta Steering \\
  \Xi Workers \\
  request? : STEER \\
  cursor? : \nat
\where
  request? \in \dom steerPhase \\
  steerPhase~request? = locked \\
  target~request? \in \dom phase \\
  phase~(target~request?) = ready \\
  now < deadline~request? \\
  steerPhase' = steerPhase \oplus \{request? \mapsto sent\} \\
  baseline' = baseline \cup \{request? \mapsto cursor?\} \\
  sentAt' = sentAt \cup \{request? \mapsto now\} \\
  admittedPhase' = admittedPhase \cup \{request? \mapsto ready\} \\
  receiptDeadline' = receiptDeadline \cup \{request? \mapsto now + 10000\} \\
  (now', target', words', deadline', inFlight') =
    (now, target, words, deadline, inFlight) \\
  (receiptSeq', receiptText', accepted', endedByReceipt') =
    (receiptSeq, receiptText, accepted, endedByReceipt)
\end{schema}

cursor? is the latest harness input sequence sampled before sending, or zero
when no input has been observed. When a permission decision is pending, cursor? instead
uses the newest admitted hook sequence. ReceiptHeard uses the worker's own later
input event. Stale or differently worded input cannot take this transition.
The profile exposes inputs since a cursor, backed by the newest 32 input
sequences per session. A later unrelated prompt does not erase a retained
matching receipt. Eviction can still cause an unheard timeout; retention
does not promise unbounded delivery history.

\section{Pending decisions and live reports}

\begin{zed}
  DecisionChoice ::= approve | deny
  \\
  HookBoundary ::= resultBoundary | otherBoundary
\end{zed}

\begin{axdef}
  permissionPrompt : WORDS
\end{axdef}

Only admitted worker events update decision state. Notification kinds
permission\_prompt and idle\_prompt retain their clipped message and sender
sequence; the next newer non-Notification event clears the question. Older
events cannot resurrect or clear a newer question.

\begin{schema}{WorkerDecisions}
  pendingDecision : WORKER \pfun (\nat \cross WORDS \cross WORDS) \\
  decisionHigh : WORKER \fun \nat \\
  promptEpoch : WORKER \fun \nat \\
  decisionReceipts : WORKER \fun \power (\nat \cross \nat)
\where
  \forall w : WORKER @ \# (decisionReceipts~w) \leq 64 \land
    promptEpoch~w \leq decisionHigh~w
\end{schema}

\begin{schema}{DecisionDelivery}
  \Xi WorkerDecisions \\
  worker? : WORKER \\
  choice? : DecisionChoice \\
  question? : \nat \\
  message? : WORDS \\
  sentChoice! : DecisionChoice
\where
  worker? \in \dom pendingDecision \\
  pendingDecision~worker? = (question?, permissionPrompt, message?) \\
  sentChoice! = choice?
\end{schema}

DecisionDelivery admits only an explicit approve or deny choice while a
permission question is pending. Its question input is the prompt\_seq copied
from the exact question announced to the person, not a sequence sampled when
the answer arrives. Delivery checks this sequence against the pending permission
question under the actor lock; a mismatch or cleared question returns ``worker
has a different prompt now'' without sending any keys. The agent must ask the
new question before answering it. Free-form steering without a choice is refused
for permission\_prompt; a choice without a pending permission question and an urgent choice are also
refused, without sending any keys. The harness maps approve to its explicit
Yes selector and deny to its decline key; no answer text is pasted into the
dialog. For Claude these are the numeric key 1 and Escape, respectively,
neither followed by Enter. A receipt includes the sent choice even on an
unheard timeout; heard acknowledges a later hook, not permission approval.
Ambiguous spoken answers require another yes/no question before delivery.
An idle\_prompt still publishes needs\_decision, but waits for ordinary text,
not permission keys. It accepts verbatim words without a choice and requires
a matching UserPromptSubmit receipt; choices are refused for idle prompts.

\begin{schema}{InitWorkerDecisions}
  WorkerDecisions
\where
  pendingDecision = \emptyset \\
  \forall w : WORKER @ decisionHigh~w = 0 \land promptEpoch~w = 0 \land
    decisionReceipts~w = \emptyset
\end{schema}

\begin{schema}{DecisionNotification}
  \Delta WorkerDecisions \\

\where
  sequence? > decisionHigh~worker? \\

  decisionHigh' = decisionHigh \oplus \{worker? \mapsto sequence?\} \\
  promptEpoch' = promptEpoch \oplus \{worker? \mapsto sequence?\} \\
  decisionReceipts' = decisionReceipts
\end{schema}

DecisionNotification admits only permission\_prompt and idle\_prompt kinds.

\begin{schema}{DecisionHookReceipt}
  \Delta WorkerDecisions \\
  worker? : WORKER \\
  sequence? : \nat \\
  question? : \nat \\
  message? : WORDS \\
  retained : \power (\nat \cross \nat)
\where
  pendingDecision~worker? = (question?, permissionPrompt, message?) \\
  sequence? > decisionHigh~worker? \\
  pendingDecision' = pendingDecision \\
  decisionHigh' = decisionHigh \\
  promptEpoch' = promptEpoch \\
  retained \subseteq (decisionReceipts~worker?) \cup \{question? \mapsto sequence?\} \\
  question? \mapsto sequence? \in retained \\
  \# retained \leq 64 \\
  decisionReceipts' = decisionReceipts \oplus \{worker? \mapsto retained\}
\end{schema}

DecisionHookReceipt runs before folding any newer hook while a permission question is
pending, including another Notification. DecisionNotification then replaces
the question for qualifying kinds; other Notifications retain the question
while advancing decisionHigh but not promptEpoch. Non-Notification events use
DecisionProgress.

\begin{schema}{DecisionProgress}
  \Delta WorkerDecisions \\
  worker? : WORKER \\
  sequence? : \nat \\
  boundary? : HookBoundary
\where
  sequence? > decisionHigh~worker? \\
  pendingDecision' = \{worker?\} \ndres pendingDecision \\
  decisionHigh' = decisionHigh \oplus \{worker? \mapsto sequence?\} \\
  boundary? = resultBoundary \implies
    promptEpoch' = promptEpoch \oplus \{worker? \mapsto sequence?\} \\
  boundary? = otherBoundary \implies promptEpoch' = promptEpoch \\
  decisionReceipts' = decisionReceipts
\end{schema}

DecisionProgress applies only to non-Notification events.
Stop selects resultBoundary; all other events select otherBoundary. A worker's
promptEpoch is the newest admitted Stop, permission\_prompt or idle\_prompt
sequence, exposed as prompt\_epoch through WorkerControl's live reports. Input
acknowledgements clear a question but do not change its epoch. Unadmitted or
stale hooks cannot advance it. The per-call steering cache uses the canonical
worker identity, exact words, urgency and prompt epoch for ordinary text, not
the provider tool-call ID. Permission choices instead use worker identity,
choice and the announced question's sequence, ignoring the re-transcribed
words. A genuine retry replays its receipt even after the question has cleared;
a choice for a different question has a different identity.
The observed epoch also accompanies delivery through WorkerControl. Under the
same actor lock used to ingest hooks, delivery reconciles the current epoch
and refuses a stale request before sending any keys. The error tells the agent
to read the new prompt and ask the person again. Direct control without a
sampled epoch targets the live prompt instead.
Permission choices always require the announced question's sequence, including
direct control; that check is never replaced by sampling the current epoch.

\begin{schema}{DecisionReceiptHeard}
  \Delta Steering \\
  \Xi WorkerDecisions \\

\where
  request? \in \dom steerPhase \\

\end{schema}

After checkpointing, admitted Stop and decision notifications publish one
provider-neutral live report per sender sequence. Decision notifications publish
only when the store's current pending question has that notification's sequence;
delayed notifications cannot ask an obsolete question. Stop reports publish only
when no newer admitted hook supersedes their sequence. A suppressed older Stop
cannot replace a queued result. A separate bounded sequence
window records successful checkpoints, so a failed checkpoint can be retried
and a still-current event filling a tracked gap publishes once. Each subscriber retains at
most 32 reports, dropping the oldest on overflow; absent subscribers lose
reports. The registry remains the durable status source. A live call sends
hidden contextual\_update immediately, then a marked voxd user\_message to
request speech: decisions immediately, finished results after two seconds
without user transcript or agent audio. Ending a call removes its subscriber
without changing workers or their pending decisions.

Admission is a server-side registry decision: the session must name an active
registered worker and cwd must equal its canonical worktree. The advisory
worker-only wire flag never establishes provenance. This is the existing
metadata admission boundary, not cryptographic authentication of a hook
process. Unmanaged context events cannot populate receipt history, even if
they reuse a worker session or sequence. Receipt retention deduplicates its
own admitted inputs independently of general context deduplication.

\section{Daemon restart}

\emph{Restart preserves result and current decision}: the boot projection
is seeded with the checkpointed result, pending question and relay order
before the next hook can be admitted. A lower sequence cannot replace the
latest result or clear the latest decision. The retained tool projection
also survives boot. The hook client retries the same stamped event for up
to five seconds; delivery across longer outages is not guaranteed.

\begin{zed}
  [CHECKPOINT, PANE]
\end{zed}

\begin{schema}{WorkerRecovery}
  saved, restored : WORKER \pfun CHECKPOINT \\
  active : \power WORKER \\
  panes : PANE \pfun WORKER \\
  owned, live : \power PANE
\where
  active \subseteq \dom saved \\
  restored \subseteq saved \\
  owned \subseteq \dom panes \\
  live \subseteq \dom panes
\end{schema}

\begin{schema}{StartupAdoptsAndReaps}
  \Delta WorkerRecovery \\
  \Delta Workers \\
  protected?, retired?, verifiedLive?, hookEligible! : \power WORKER
\where
  active = \dom (phase \rres \{starting, ready\}) \\
  retired? \subseteq active \\
  retired? \cap \ran (live \dres panes) = \emptyset \\
  verifiedLive? \subseteq active \cap \ran (live \dres panes) \\
  hookEligible! = verifiedLive? \\
  active \setminus retired? \subseteq protected? \\
  retired? \cap protected? = \emptyset \\
  saved' = saved \\
  active' = active \setminus retired? \\
  phase' = phase \oplus \{ w : retired? @ w \mapsto exited \} \\
  report' = report \\
  readySeen' = readySeen \\
  pending' = pending \cup retired? \\
  restored' = active' \dres saved \\
  panes' = panes \\
  owned' = owned \\
  live' = live \setminus \{ p : owned | panes~p \notin protected? \}
\end{schema}

\emph{Startup retires dead workers before hook admission}:
\textit{retired?} names the workers confirmed dead and checkpointed as
\textit{exited}, not a new worker state. Their work products are retained.
The \textit{hookEligible!} set describes ordinary active hook admission.
Startup adds them to \textit{pending}, enabling background
\textit{RetryCleanup} or a retry through explicit stop. The daemon serves
requests after recovery. Independent tmux
probes run concurrently with a shared deadline; an inconclusive probe leaves
the registration protected without admitting ordinary active hooks until a
later positive liveness observation. A protected worker whose liveness is
unknown can still send a notification or terminal report; neither confirms
that it is live or exited. Other managed hook attempts are denied with a
retry indication, within the same five-second delivery budget.
A confirmed exit observed during a worker
listing is checkpointed and schedules trust cleanup without waiting for
the harness configuration lock.

\emph{Startup only reaps marked orphans}: the reaper removes only a pane
marked as owned by this registry and not protected by a live or unreadable
registry record. The reaper never modifies an inherited harness config.
Credentials are transferred by a private Unix socket and not written to
a dedicated credential file; private brokers are removed separately when
their recorded owner process no longer exists.
